# Slice 02b — Transactional PostgreSQL memory
Prior head f23f8258a588b825c0582dd684ba544bdaf15a73 passed both push 43645474404 and PR 43645477318. This slice adds the Rust world-memory crate and a real PostgreSQL migration/integration workflow, not a new service or UI.

## Design and deviations
Use postgres 0.19.14 (synchronous Rust client, https://docs.rs/crate/postgres/0.19.14) for the first isolated transaction adapter instead of candidate SQLx. A later async server must use bounded blocking execution or change the adapter after measurement; do not block the web executor. Existing kernel remains authoritative. PostgreSQL row locking and Read Committed: https://www.postgresql.org/docs/18/explicit-locking.html and https://www.postgresql.org/docs/18/transaction-iso.html. Every storage operation locks a single head row and rebuilds the kernel from the ordered log, then admits at most one event and appends it and updates the head in a single transaction. Receipt is returned only after commit. Retry identical commands on ambiguous commit outcomes, never invent new command IDs. Unique (actor, command) and (work, revision); sequence continuity, envelope-vs-column consistency and head/log count checked. These checks detect common corruption/truncation but do not prove tamper-evidence against a privileged attacker.

An initial deliberately bounded full-replay design (5000 events, 64 MiB record text, 5000 principals) chooses correctness over scale. Global serialization, replay on reads and latency/timing leakage are unresolved; no throughput or production performance claim. Schema is private to a trusted non-owner service role with select/insert on history, read-only principals, update only the head counter. This is not tenant-level RLS: the runtime can see all history by design. Never expose the DB, internal receipts, or principal selection to users or an AI. No real identity, membership changes or role binding, cross-tenant threat model, user deletion/retention/redaction, TLS, encrypted storage, durable backup/restore, migrations upgrade/down policy or secret management has been signed off. No live data may enter this slice until those boundaries are implemented and reviewed. CI uses disposable loopback PostgreSQL, plaintext synthetic passwords and NoTls only in the test. No deployment.

Integration test covers closing/reopening database connections, replay, idempotence, scope denial, concurrent revision race, revocation, restricted role write denial, transaction rollback on injected constraint failure and fail-closed detection of a missing log tail. It does not simulate a process crash, database server restart or backup restore yet. New dependency resolution and format/compile/integration results pending. The expanded generated Cargo.lock must be captured from CI and committed before restoring mandatory locked builds; original lock has not been manually altered. The temporary workflow resolves dependencies independently in kernel and PostgreSQL jobs; final head must use one committed lock and rerun all checks.
