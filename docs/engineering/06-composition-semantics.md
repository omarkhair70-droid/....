# Slice 03a — Composition Engine: evidence and local change
15 November 2026. Prior exact head b32657bfb5d86e7779ce8395f7a90bc0ff171728 passed push 43646203759 and PR 43646209728. Continuation of research 02/04 and production decision 05. Adds a real Rust library without new third-party dependencies. This is not an interface, proof of commercial value, or model.

## Semantics
Candidate = stable ID + scope + work ID/revision + intended outcome + proposed roles + explicit hard/optional propositions. A role is a proposal, not a statement of authority or consent. The initial engine evaluates supplied candidate configurations; it does NOT yet discover or generate them. Exact contextual claim IDs and already authorized, upstream-admitted evidence with versioned source pointers are inputs. No identity resolver, citation verifier, claim extraction, or source retrieval yet. Distinct source pointers do not establish independence or truth; no numeric confidence or votes.

K(q,t) = (any active supporting evidence, any active opposing evidence), with active meaning not withdrawn and valid_from <= t < valid_until (if present). Unknown, Supported, Opposed, Contested. If a hard proposition has only opposition, BlockedUnderEvidence; otherwise if any declared condition lacks unopposed support (including optional opposition), Conditional; otherwise SupportedUnderEvidence. No completeness guarantee, work execution, or human commitment inferred. This deliberately conservative rule is a candidate-policy choice requiring review. At least one hard requirement is mandatory to avoid vacuous support. No ranking or automated external action.

Reverse claim -> candidate index defines one-hop dependents. An evidence update validates scope, ID, monotonically increasing revision, source revision and time interval, then evaluates only candidates that depend on the claim. Explicit time advance scans bounded evidence for activity changes. Output distinguishes evaluated candidates from those whose conditions or evidence traces changed. Work identity/revision is retained; candidate versions are immutable here. No arbitrary transitive rule graph or solver yet. No automatic writes to Kernel, PostgreSQL, or AI. Scope mismatch is refused, but the caller must actually authorize the snapshot, provenance, work and grant lifecycle. The cache must be discarded/rebuilt on authorization changes; no cross-user reuse. Untrusted data must not reach this port without bounded validation and scope enforcement.

Bounds: 10k evidence, 1k candidates, 32 requirements and 16 roles each; text lengths bounded by Unicode scalar count. Worst-case repeated trace storage may still be large; performance and memory benchmarks are pending, as are pagination and provenance compression. Explicit monotonic logical time, not a wall-clock task or scheduler. Evidence latest revision is kept in memory only; earlier versions are not archived here; upstream durable evidence events and snapshots are necessary for historical rebuild. Candidate edits, typed wire contracts, work binding, source admission, incremental persistent state and AI proposal generation follow later. No claim of global novelty or full noninterference.

## Verification
Six synthetic Rust tests cover four knowledge states, expiry/future activation, scoped evidence and identity rejection, optional conditions, idempotent replay, targeted invalidation and comparison against full recomputation over fixed-seed changes. New tests have not run at authoring time. No new third-party dependencies; Cargo must add workspace metadata to the lockfile. CI temporarily resolves with cargo fetch and emits the generated lock for capture, then restore locked mode. Prior identity/retention/backup/security gates remain open; no real data, merge or deployment.
